Section One

The Problem

Why AI-assisted development needs a methodology

The Reality

AI Can Code Fast.
But Fast ≠ Right.

What Goes Wrong

✗ AI writes the wrong thing because requirements are vague
✗ "Make login secure" means different things to everyone
✗ No tests — bugs hide until production
✗ AI runs ahead, makes changes you didn't approve
✗ A typo fix gets the same ceremony as a feature
✗ Same bugs keep coming back — no root cause analysis
✗ No documentation, no traceability, no audit trail

How Vibecoding Fixes It

✓ Detailed specs with testable criteria eliminate ambiguity
✓ Given/When/Then format — zero room for interpretation
✓ TDD + quality gates catch issues before users do
✓ Stop & Wait protocol — you approve every phase
✓ 5 adaptive tiers match process to change size
✓ 5 Whys post-mortems prevent repeat bugs
✓ Auto-generated docs, traceability matrix, memory

Auto-Detection

How Tiers Are Chosen

The workflow analyzes keywords, scope, and file count in your request.

MINIMAL Signals

typo, spelling, copy, wording, rename, color, padding, margin, config, env variable, "change X to Y"

LIGHT Signals

fix, bug, broken, crash, error, wrong, add a button, small component, refactor, extract, move, 1-3 files

STANDARD Signals

feature, implement, build, create, add (new functionality), form, page, API endpoint, database, 3-10 files

FULL Signals

epic, major, architecture, redesign, migration, security overhaul, system, platform, 10+ files

You always have control. Override any time: --minimal --light --standard --full
Or just say: "actually make this STANDARD"

Phase 1

Specification

Define exactly what to build with Given/When/Then acceptance criteria.

What Gets Created

docs/specs/user-authentication.md # Feature: User Authentication ## Acceptance Criteria ### AC-001: Successful login GIVEN a registered user on the login page WHEN they enter valid email and password AND click "Sign In" THEN they are redirected to dashboard AND see welcome message with their name AND session is created with 24h expiry ### AC-002: Failed login GIVEN a user on the login page WHEN they enter an invalid password THEN they see "Invalid email or password" AND the password field is cleared AND failed attempt counter increments

Why It Matters

Zero Ambiguity

Each criterion is testable. "Make login secure" becomes 5-6 precise acceptance criteria.

Cheapest Place to Change

Fixing a spec line costs nothing. Fixing implemented code costs a full TDD cycle.

Contract With AI

The spec is what AI implements. Clear spec = correct implementation. Vague spec = rework.

🛑 STOP & WAIT
You must approve the spec before any code is written.

Phase 2

Test Planning

Plan exactly how each acceptance criterion will be verified.

AC Level Test File Test Name Edge Cases
AC-001 Integration login.test.ts should redirect on valid login Empty fields, whitespace email
AC-002 Integration login.test.ts should show error on invalid password SQL injection, XSS in email
AC-003 Unit + E2E login.test.ts should lock after 3 failed attempts Rapid successive attempts, race conditions

🛑 STOP & WAIT — You approve the test plan before implementation begins.

Phase 3

TDD Implementation

Red → Green → Blue. For every acceptance criterion.

RED

Write Failing Test

Test must actually fail. This proves the test is valid and catches a real behavior.

// This MUST fail first test('should redirect on valid login', () => { render(<LoginPage />); // ... test the behavior expect(result).toBe('dashboard'); }); // ✗ FAIL — LoginPage doesn't exist yet
GREEN

Minimum Code to Pass

Write the simplest code that makes the test pass. No over-engineering. No extras.

// Just enough to pass function LoginPage() { // implement login logic // redirect on success return <form>...</form>; } // ✓ PASS
BLUE

Refactor Safely

Improve code quality, extract helpers, clean up — while keeping all tests passing.

// Extract, simplify, improve const { handleLogin } = useAuth(); // All tests still passing // ✓ PASS — safe to move on // Update traceability matrix: // AC-001 → login.test.ts → PASSED

This cycle repeats for every AC: AC-001, AC-002, AC-003... until all pass.

Resilience

Error Recovery

Every skill has structured failure handling. No improvising when things break.

3 Recovery Principles

1. After ANY fix → re-run ALL checks

Never re-run just the one that failed. A fix can break other things.

2. Report honestly — never guess

If stuck after reasonable effort, stop and ask for guidance. Don't fabricate solutions.

3. Escalate scope when needed

If a /fix turns complex (3+ files, unclear cause), upgrade to STANDARD with /vibe feature.

Section Twelve

Pro Tips

Hard-won lessons for maximum productivity

Dos

What to Do

  • 1Be specific in requests. "Add notification bell with unread count badge and dropdown of last 10" beats "add notifications." More detail = fewer revision cycles.
  • 2Actually read the spec. When ACs come back, review them carefully. Catching a misunderstanding here costs nothing. In code, it costs a full TDD cycle.
  • 3Override tiers when your gut says to. Auto-detection is good, not perfect. If something feels bigger than LIGHT, append --standard.
  • 4Add use context7 for library work. Fetches live documentation instead of relying on training data. Essential for Next.js, React, Tailwind, etc.
  • 5Commit after every feature. Use /ship after approval. Small, frequent commits beat big merges.
  • 6Start every session with /status. Know where you left off. Workflow state persists across sessions.
  • 7Use /mock-data-doc for backend handoff. One command generates a complete backend spec from your prototype. Saves days of back-and-forth.
  • 8Batch related small changes. Instead of 5 MINIMAL requests, describe them together in one /vibe tweak.
Don'ts

Common Mistakes

✗ Applying STANDARD to a typo

Use /fix or /vibe tweak. A typo doesn't need a spec, test plan, and review ceremony.

✗ Skipping spec review

Just saying "approved" without reading the ACs. 2 minutes here saves hours of rework later.

✗ Building everything at once

One feature at a time. Use /worktree only for truly independent parallel work.

✗ Going straight to production mode

Always prototype first. Validate with users. Then upgrade when the idea is proven.

✗ Not committing after features

Use /ship after approval. Uncommitted work is lost work.

✗ Fixing bugs without analysis

Use /bug for root cause analysis. Quick fixes without understanding cause repeat bugs.
